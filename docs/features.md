# Features & Core Logic

## 1. Authentication & Authorization (ระบบสมาชิก)
- **Google Login:** เข้าสู่ระบบด้วยอีเมล Google (OAuth2)
- **First-time Setup:** หากล็อกอินครั้งแรก ระบบจะให้เลือก "สถานบริการ (รพ.สต.)" ที่สังกัด 
- **Approval Workflow:** หลังจากเลือกสถานบริการ สถานะผู้ใช้จะเป็น `pending` และต้องรอให้ Super Admin อนุมัติเป็น `approved` จึงจะสามารถเข้าถึงข้อมูลได้ เฉพาะสถานะ `approved` เท่านั้นที่เข้าสู่ระบบและเรียกใช้งานได้ ทุก Role รวม admin และ superadmin (Issue #158, [`CONTEXT.md`](../CONTEXT.md) §34) สถานะอื่นทุกค่าถูกปฏิเสธตั้งแต่เข้าสู่ระบบ
- **Session End (Issue #155, [`CONTEXT.md`](../CONTEXT.md) §51):** เมื่อได้ 401 ไม่ว่าสาเหตุใด ระบบพาไปหน้าเข้าสู่ระบบจากทุกหน้า รวมถึง Dashboard สาธารณะ และแจ้ง "เซสชันสิ้นสุดแล้ว กรุณาเข้าสู่ระบบอีกครั้ง" ข้อความเดียวไม่แยกสาเหตุ ผู้ใช้ที่ถูกเปลี่ยนสถานะการอนุมัติจะทราบเหตุผลเมื่อเข้าสู่ระบบอีกครั้ง การออกจากระบบเองไม่แสดงข้อความนี้ ข้อความอยู่จนกว่าจะเริ่มเข้าสู่ระบบใหม่หรือรีเฟรชหน้า
- **Role-based Access Control (RBAC):** 
  - **User:** ดูข้อมูลเฉพาะสถานบริการของตนเอง
  - **Admin / Super Admin / สสอ. (00588):** ดูข้อมูลของทุกสถานบริการได้ทั้งหมด

## 2. Data Upload & Processing (การนำเข้าข้อมูล)
- **Excel / JSON Parsing:** อ่านไฟล์ HDC กลุ่มอายุ 1, 2, 3 และ 5 ปีจากเบราว์เซอร์ ตรวจทุกแถวและรักษาคอลัมน์ว่าง
- **Data Cleaning:** 
  - แปลงค่า `<NA>` เป็น `null`
  - คอลัมน์ที่ชื่อมีคำว่า `hosc` หรือ `hosp` จะถูกบังคับให้อ่านค่าเป็น String เพื่อรักษาเลข `0` นำหน้า
- **Upsert:** ใช้ PID + หน่วยบริการ + ปีงบประมาณ + sex + birth + check_vhid ต้องตรงกันทั้งหมด CID ที่ปิดบังด้วย `*` ซ้ำกันได้จึงไม่ใช้เป็นตัวระบุ ถ้าไม่มี PID ต้องมี CID ไม่ปิดบังแทน โดยยังตรงส่วนประกอบอื่นครบ ไม่ใช้ CID สำรองจับคู่ข้ามคีย์
- **Update:** คอลัมน์ไม่ได้ส่งมารักษาค่าเดิม เซลล์ว่าง/null ที่ส่งมาล้างค่านั้น
- **Data Sync:** ค่าเริ่มต้นเป็นเติมข้อมูล ไม่ deactivate คนที่ไม่อยู่ในไฟล์ โหมดซิงค์ไฟล์เต็มจะ deactivate ได้เมื่อรับครบทุก chunk และเฉพาะปี/หน่วยบริการของ batch ที่ตรวจแล้ว การนำเข้าเสร็จ (รวมการ deactivate) ในคำขอเดียวกับ chunk สุดท้ายที่ server รับ ไม่มีขั้นแยกที่หน้าเว็บต้องเรียกต่อ (Issue #144, [ADR-0011](adr/0011-last-chunk-finalizes-the-import.md))
- **Lost Response ระหว่างนำเข้า (Issue #156, [`CONTEXT.md`](../CONTEXT.md) §50):** ถ้าไม่ได้รับคำตอบของ chunk ใด หน้าอัปโหลดหยุดส่ง chunk ทันทีและไม่ส่ง chunk ซ้ำเอง แล้วตรวจผลจากตัวอย่างของ "ย้อนการนำเข้าล่าสุด" ของกลุ่มอายุและปีงบประมาณเดียวกัน
  - การนำเข้าล่าสุดที่เขียนข้อมูลเป็นชุดนี้และปิดการนำเข้าแล้ว: ถือว่านำเข้าสำเร็จ เขียน Dashboard Summary ตามปกติ และหน้าผลแจ้งว่าไม่ได้รับจำนวนรายการจากเซิร์ฟเวอร์แทนการแสดงตัวเลข
  - ยังไม่ปิดการนำเข้าชุดนี้, เป็นการนำเข้าชุดอื่น หรือยังไม่มีการนำเข้า: แจ้งให้นำเข้าไฟล์ใหม่อีกครั้ง
  - ตรวจผลไม่สำเร็จ: แจ้งให้ดูส่วน "ย้อนการนำเข้าล่าสุด" ก่อนนำเข้าอีกครั้ง เพราะการนำเข้าไฟล์เดิมซ้ำหลังชุดก่อนปิดการนำเข้าแล้วจะสร้างการนำเข้าใหม่ที่อัปเดตเด็กเดิม ซึ่งย้อนการนำเข้าไม่ได้
- **ปีงบประมาณของหน้าอัปโหลด (Issue #136):** ไม่มีค่าเริ่มต้น ผู้นำเข้าต้องเลือกปีงบประมาณเองก่อน ส่วนรับไฟล์ ปุ่มนำเข้า และปุ่ม "ประมวลผล Dashboard ใหม่" ใช้ไม่ได้จนกว่าจะเลือกปี เมื่อนำเข้าเสร็จ ปีที่เลือกยังคงอยู่สำหรับไฟล์ถัดไปในรอบเดียวกัน (โหลดหน้าใหม่จะกลับเป็นค่าว่าง)
- **ตรวจก่อนนำเข้า (Issue #111):** ทุกการนำเข้าต้องผ่านขั้นตรวจแบบอ่านอย่างเดียวก่อนเขียนข้อมูล หน้าอัปโหลดแสดงตารางเป้าหมาย ปีงบประมาณ และจำนวนที่จับคู่กับเด็กเดิมได้ / รายชื่อใหม่ / จะปิดสถานะ (เฉพาะโหมดซิงค์) แยกรายหน่วยบริการ ให้กดยืนยันก่อนเริ่มนำเข้าทุกครั้ง ถ้าเข้าเงื่อนไขเสี่ยง ผู้นำเข้าต้องพิมพ์ตัวเลขยืนยัน และ server ต้องตรวจตัวเลขนั้นก่อนรับข้อมูล
  - เงื่อนไขเสี่ยง (ทั้งสองโหมด): หน่วยบริการในไฟล์มีเด็กที่เปิดใช้งานอยู่ในปีงบเดียวกัน แต่จับคู่ได้ 0 คน (คิดรายหน่วยบริการ)
  - เงื่อนไขเสี่ยง (เฉพาะโหมดซิงค์): จะปิดสถานะเกิน **20%** ของเด็กที่เปิดใช้งานอยู่ในหน่วยบริการที่อยู่ในไฟล์ (คิดรวมทุกหน่วย) เกณฑ์นี้เป็นค่าคงที่ `EPI_SYNC_SHRINK_THRESHOLD` ใน backend
  - เงื่อนไขเสี่ยง (ทั้งสองโหมด, Issue #136): มีรายชื่อในไฟล์อย่างน้อย 1 รายการที่วันเกิดอยู่นอก Cohort Birth Range ของกลุ่มอายุและปีงบประมาณที่เลือก ([`CONTEXT.md`](../CONTEXT.md) §46) (UI เรียก "กลุ่มเกิดของปีงบประมาณ" ไม่ใช้คำ "ช่วงวันเกิด" ซึ่งหมายถึง Birth Window ของกฎ) ไม่ว่าปีนั้นจะมีเด็กเดิมหรือไม่ ไฟล์ HDC ที่ถูกต้องมีเด็กอยู่ในกลุ่มเกิดนี้ทั้งหมด และรายการที่อยู่นอกกลุ่มเกิดจะไม่แสดงในมุมมองหรือ Dashboard Summary ใด ๆ ของปีนั้น หน้าตรวจแสดงจำนวนที่ไม่อยู่ในกลุ่มเกิดทั้งหมดและรายหน่วยบริการ (คอลัมน์ "ไม่อยู่ในกลุ่มเกิด" แสดงเฉพาะเมื่อมี) พร้อมวันเกิดต้นและปลายของกลุ่มเกิดที่ใช้ตรวจ ถ้าวันเกิดที่อยู่นอกกลุ่มเกิดทั้งหมดตรงกับปีงบประมาณเดียวกันของกลุ่มอายุที่เลือก จะแจ้งว่า "วันเกิดตรงกับปีงบประมาณ X" ถ้าตรงหลายปีจะแจ้งเฉพาะจำนวน
  - "จับคู่ได้" ในเงื่อนไขแรกนับเฉพาะเด็กที่เปิดใช้งานอยู่ ไฟล์ที่ตรงกับเฉพาะแถวที่ปิดสถานะไปแล้วจะถูกเตือน เพราะการนำเข้าจะเปิดแถวเหล่านั้นกลับมา
  - ตัวเลขที่ต้องพิมพ์ แยกหนึ่งตัวต่อเงื่อนไขที่เข้า (Issue #136) และต้องพิมพ์ถูกทุกตัว ข้อเตือนหนึ่งจึงไม่บังข้อเตือนอื่น: เงื่อนไขเด็กเดิม (จับคู่ได้ 0 คน หรือปิดสถานะเกินเกณฑ์) โหมดซิงค์ใช้จำนวนเด็กเดิมที่จะถูกปิดสถานะ, โหมดเติมข้อมูลใช้จำนวนรายชื่อในไฟล์ที่ไม่ตรงกับเด็กที่เปิดใช้งานอยู่ (รายชื่อใหม่ + ที่จะถูกเปิดสถานะกลับ); เงื่อนไขกลุ่มเกิดใช้จำนวนรายชื่อที่ไม่อยู่ในกลุ่มเกิด ต้องเป็นผู้ที่ทำการตรวจเป็นผู้พิมพ์ยืนยัน
  - ยกเลิกหลังตรวจแล้วข้อมูลไม่เปลี่ยน และไม่ทำให้การนำเข้ารอบต่อไปถูกปฏิเสธ กลไกดู [HDC column upgrade](hdc-column-upgrade.md#upload--update)
- **ย้อนการนำเข้าล่าสุด (Import Undo, Issue #139 / #112, [ADR-0009](adr/0009-import-undo-is-exact-or-refused.md), [`CONTEXT.md`](../CONTEXT.md) §47):** admin และ superadmin ย้อนผลของการนำเข้าครั้งล่าสุดที่เขียนข้อมูลแล้วของ (ตารางกลุ่มอายุ, ปีงบประมาณ) หนึ่งชุดได้จากหน้าอัปโหลด โดยไม่ต้องใช้ไฟล์ ผู้ใช้หน่วยบริการทำไม่ได้ ทุกกฎตรวจที่ server
  - ย้อนเฉพาะว่ารายการใดเป็น Active Record: แถวที่การนำเข้านั้นเพิ่มเข้ามาถูกปิดสถานะ (ไม่ลบ) และแถวที่ขั้น cleanup ของการนำเข้านั้นปิดสถานะถูกเปิดคืน เด็กที่ถูกปิดสถานะโดยการนำเข้าก่อนหน้า (ย้ายออกจริง) คงปิดสถานะตามเดิม ไม่คืนค่าวัคซีนที่ถูกเขียนทับ
  - ส่วน "ย้อนการนำเข้าล่าสุด" มีตัวเลือกกลุ่มอายุและปีงบประมาณของตัวเอง ไม่มีค่าเริ่มต้น เมื่อเลือกครบ server คำนวณตัวอย่าง: ตารางและปีงบประมาณ (แสดงเด่น) เวลานำเข้า ผู้นำเข้า วิธีนำเข้า จำนวนที่จะปิดสถานะและเปิดสถานะคืนรายหน่วยบริการ และเตือนเมื่อหลังย้อนไม่เหลือ Active Records แล้วกดยืนยันครั้งเดียว ยกเลิกแล้วไม่มีอะไรถูกส่ง
  - ปฏิเสธ (พร้อมเหตุผลภาษาไทย) เมื่อ: ไม่มีการนำเข้าที่เขียนข้อมูลของตารางและปีนั้น, การนำเข้าล่าสุดยังอัปโหลดไม่เสร็จ, ถูกย้อนไปแล้ว (ย้อนได้ขั้นเดียว และ batch ที่ย้อนแล้วยังกันการย้อน batch ก่อนหน้า), นำเข้าก่อนมีระบบนี้, อัปเดตเด็กที่มีอยู่แล้วอย่างน้อย 1 แถว (รวมการเปิดสถานะคืน), หรือมีการนำเข้าที่ใหม่กว่าเขียนตารางและปีเดียวกัน ตอนยืนยัน server ตรวจซ้ำและปฏิเสธถ้าตัวเลขต่างจากตัวอย่าง (ตัวอย่างล้าสมัย)
  - **วิธีกู้คืนหลัก** เมื่อย้อนไม่ได้ คือนำเข้าไฟล์ที่ถูกต้องอีกครั้งแบบ "ซิงค์ไฟล์เต็ม" ซึ่งผ่านขั้นตรวจก่อนนำเข้าตามปกติ และคืนค่าที่ถูกเขียนทับได้ด้วย
  - หลังย้อน: ถ้าตารางและปีนั้นไม่เหลือ Active Records ในหน่วยบริการใดเลย server ลบสรุป Dashboard ของตารางและปีนั้นทั้งหมด (`_all`, Q1–Q4 และ id แบบเดิม) ในการทำงานเดียวกัน Dashboard จึงแสดง "ไม่มีข้อมูลสรุป" ([`CONTEXT.md`](../CONTEXT.md) §44) ถ้ายังเหลือ หน้าเว็บเขียนสรุปใหม่ด้วยเส้นทางเดียวกับหลังนำเข้า ถ้าเขียนสรุปไม่สำเร็จจะแจ้งให้กด "ประมวลผล Dashboard ใหม่" แล้ว Dashboard และหน้าเปรียบเทียบรีเฟรช
  - ทุกการย้อนบันทึก audit `undo_epi_import` (batch ตาราง ปี วิธีนำเข้า จำนวน รหัสหน่วยบริการ และการลบสรุป ไม่มีข้อมูลรายบุคคล) กลไก receipt ดู [HDC column upgrade](hdc-column-upgrade.md#upload--update)
  - **การย้อนที่ยังไม่เสร็จ (Unfinished Import Undo, Issue #140, [ADR-0010](adr/0010-import-undo-finishes-or-stays-unfinished.md), [`CONTEXT.md`](../CONTEXT.md) §47):** ถ้าการย้อนหยุดกลางทาง (Sheets ขัดข้องหรือหมดเวลา) การนำเข้านั้นนับว่าย้อนแล้วเมื่อทุกขั้นเสร็จเท่านั้น หน้าเว็บโหลดตัวอย่างใหม่ทันทีหลังการย้อนล้มเหลว และส่วน "ย้อนการนำเข้าล่าสุด" แสดง "การย้อนที่ยังไม่เสร็จ" พร้อมตารางและปีงบประมาณ ผู้เริ่มย้อนและเวลา จำนวนรวมที่จะปิดสถานะและเปิดสถานะคืนตามแผนเดิม และคำเตือนลบสรุป (คิดจาก Active Records ขณะนั้น) แล้วกด "ย้อนต่อให้เสร็จ" ครั้งเดียว admin คนใดก็ทำต่อได้
    - ทำต่อเฉพาะขั้นที่ยังไม่เสร็จ ไม่เขียนซ้ำ audit มีรายการเดียวที่ระบุผู้เริ่มย้อนและจำนวนตามแผน (บันทึกผู้ทำต่อถ้าเป็นคนอื่น) ถ้าข้อมูลไม่ตรงทั้งกับแผนและกับสภาพที่ย้อนเสร็จแล้ว (เช่น มีการแก้ชีตด้วยมือ) จะปฏิเสธและให้ติดต่อผู้ดูแลระบบ เจ้าของระบบคืนแถวให้ตรงแผนด้วยมือ บันทึก audit `manual_data_fix` แล้วกด "ย้อนต่อให้เสร็จ"
    - ระหว่างที่ยังไม่เสร็จ การนำเข้าของกลุ่มอายุและปีงบประมาณนั้นถูกปฏิเสธทั้งตอนตรวจก่อนนำเข้าและตอนเขียนชุดข้อมูลแรก (ทุกหน่วยบริการ) พร้อมข้อความที่ระบุตารางและปีงบประมาณและชี้ไปที่ "ย้อนการนำเข้าล่าสุด" ตารางหรือปีอื่นนำเข้าได้ตามปกติ Summary Regeneration ไม่เปลี่ยน
- **สร้าง Dashboard Summary เฉพาะตารางที่มีข้อมูล (Issue #134 / #115):** ทั้งขั้นสร้างสรุปหลังนำเข้าและ Summary Regeneration ("ประมวลผล Dashboard ใหม่") ใช้กฎเดียวกัน คือจะเขียนสรุปของ (ตารางกลุ่มอายุ, ปีงบประมาณ) ก็ต่อเมื่อตารางนั้นมี Active Records ของปีนั้นอย่างน้อย 1 รายการ (ทั้งอำเภอ) ([`CONTEXT.md`](../CONTEXT.md) §44)
  - ตารางที่ไม่มี Active Records ถูกข้ามทั้งหมด ไม่เขียนทั้ง `_all` และ Q1–Q4 และแถวสรุปเดิมของตารางนั้นคงไว้ตามเดิม
  - ไตรมาสที่ไม่มีเด็ก หรือกลุ่มเกิดประจำปีที่ว่าง ภายในตารางที่มี Active Records ยังบันทึกเป็น 0 จริงตามเดิม
  - Summary Regeneration: ประมวลผลครบ 4 กลุ่มอายุ → แจ้งสำเร็จ, ข้ามบางกลุ่ม → แจ้งเตือนระบุปีงบประมาณและกลุ่มอายุที่ถูกข้าม, ข้ามทั้ง 4 กลุ่ม → แจ้งข้อผิดพลาดและไม่บันทึกอะไรเลย กล่องยืนยันระบุปีงบประมาณในหัวเรื่องและรายชื่อ 4 กลุ่มอายุก่อนเริ่ม
  - หลังนำเข้า: ถ้าตารางที่นำเข้าไม่เหลือ Active Records ของปีนั้น (เช่น ซิงค์ไฟล์เต็มปิดสถานะทั้งหมด) การนำเข้ายังสำเร็จพร้อมตัวเลขเดิม และแจ้งว่า "ไม่ได้สร้างสรุปเพราะไม่มีรายการที่เปิดใช้งาน"
- **As of Date:** บันทึกเวลาที่ทำการอัปโหลดลงใน `audit_logs` เพื่อให้หน้า Dashboard นำไปแสดงว่า "ข้อมูลอัปเดตล่าสุด ณ วันที่..." ผู้ใช้ทุกสถานะอ่านได้ผ่าน `getLatestImportTime` ซึ่งคืนเฉพาะ timestamp ล่าสุดของการนำเข้า (data-minimized) ส่วนการอ่าน `audit_logs` ฉบับเต็มยังเป็นสิทธิ์ admin

## 3. EPI Tracking Dashboard (ระบบติดตามวัคซีน)
### 3.1 เกณฑ์การประเมินและการติดตามวัคซีน (อ้างอิงมาตรฐาน HDC)
หน้า EPI Tracking ของแต่ละกลุ่มอายุแสดง **2 มุมมอง** ได้แก่ มุมมองที่ 1 (รายชนิดวัคซีน) และมุมมองที่ 2 (Fully Immunized) จากข้อมูลรายบุคคลที่นำเข้า โดย **ไม่มีแท็บภาพรวม (OpenData) ในหน้า EPI Tracking** ข้อมูลรวม HDC OpenData ยังคงอยู่ใน cache ฝั่ง Backend สำหรับงานข้อมูลที่แยกต่างหาก

มุมมองที่ 2 สำหรับเด็กอายุ 1, 2, 3 และ 5 ปีตัดสินผลรายคนและ summary ด้วยกฎ View 2 ในชีต `vaccine_rules` (Issue #101, [ADR-0006](adr/0006-vaccine-rules-sheet-is-staff-owned-primary-source.md)) ค่า `result` ที่นำเข้าจาก HDC แสดงประกอบ ไม่เปลี่ยนผลตามกฎ และรายชื่อติดป้าย "ผลไม่ตรงกับ HDC" (HDC Result Mismatch, `CONTEXT.md` §43) เฉพาะเมื่อทั้งสองฝ่ายตัดสินผ่าน/ไม่ผ่านแล้วขัดกัน คือกฎไม่ผ่านแต่ HDC `ผ่าน` หรือกฎผ่านแต่ HDC `ไม่ผ่าน` — View 2 Pending ตรวจสอบประวัติ (#102) ประเมินไม่ได้ และ `result` ว่างหรือค่าที่ระบบไม่รู้จักไม่ใช่คำตัดสิน จึงไม่ติดป้าย ผลตามกฎและป้ายนี้แสดงทั้งในรายชื่อและในหน้าประวัติวัคซีนข้าง "ผลจาก HDC" ถ้าไม่มีกฎ View 2 ที่เปิดใช้เลย เด็กทุกคนเป็นประเมินไม่ได้ ไม่ใช่ผ่าน รายละเอียดการแสดงผลดู [การแสดงข้อมูลรายบุคคลจาก HDC](hdc-record-display.md)

> **ข้อกำหนดปัจจุบัน:** รายการแสดงมุมมองที่ 1 แยกอายุและข้อจำกัด mapping ใช้ [HDC column upgrade](hdc-column-upgrade.md) รายละเอียดรายเข็มด้านล่างเป็นข้อมูลอ้างอิงเดิมที่ต้องอ่านร่วมกับข้อจำกัดนี้

> **แหล่งหลักของรายการวัคซีน ([ADR-0006](adr/0006-vaccine-rules-sheet-is-staff-owned-primary-source.md)):** รายการวัคซีนที่เด็กแต่ละกลุ่มอายุควรได้รับในแต่ละปีงบประมาณคือกฎในชีต `vaccine_rules` ที่เจ้าหน้าที่ตั้งค่าผ่านหน้า Rules Engine ทุกปี ระบบเป็นระบบติดตามการทำงานให้เด็กได้รับวัคซีนตามที่กระทรวงกำหนด รายการรายเข็มในหัวข้อนี้เป็นค่าตั้งต้นของ `seedVaccineRules` และข้อมูลอ้างอิง ไม่ทับค่าที่เจ้าหน้าที่ตั้งไว้ ส่วนที่เอกสารนี้กำหนดคือวิธีตีความกฎ (ALL/ANY/BRANCH, อายุเป้าหมาย, การตรวจวันที่, ประเมินไม่ได้) ผลตามกฎเป็นหลักเหนือ `result` ของ HDC (#101) การคงสถานะไม่ผ่านของเด็กที่ขาดเข็มจริง (#103) และสถานะ "ตรวจสอบประวัติ" ของคำเตือนวันที่ (#102, §3.6) ดำเนินการแล้ว

**มุมมองที่ 1: การติดตามวัคซีนรายไตรมาส / รายช่วงอายุ (อ้างอิง HDC Report 1)**
ใช้สำหรับแจ้งเตือนเจ้าหน้าที่ (รายบุคคล) ว่าเด็กอายุถึงเกณฑ์แล้วขาดวัคซีนตัวไหนบ้าง (อ้างอิงชื่อคอลัมน์จากฐานข้อมูล):
- **แรกเกิด (0-1 เดือน):** BCG แรกเกิด (`bcg_date`), HBV แรกเกิด (`hbv1_date`)
- **2 เดือน:** DTP 2 เดือน (`dtp1_date`), HBV 2 เดือน (`hbv2_date`), Hib 2 เดือน (`hib1_date`), IPV 2 เดือน (`ipv1_date`), Rota 2 เดือน (`rv21_date` หรือ `rv31_date`), PCV 2 เดือน (`pcv1_date`)
- **4 เดือน:** DTP 4 เดือน (`dtp2_date`), HBV 4 เดือน (`hbv4_date`), Hib 4 เดือน (`hib2_date`), IPV 4 เดือน (`ipv2_date`), Rota เข็ม 2 (`rv22_date` หรือ `rv32_date`), PCV 4 เดือน (`pcv2_date`)
- **6 เดือน:** DTP 6 เดือน (`dtp3_date`), HBV 6 เดือน (`hbv3_date`), Hib 6 เดือน (`hib3_date`), OPV 6 เดือน (`opv3_date`, รหัส HDC 083), Rota เข็ม 3 (`rv33_date` - ถ้ามี), PCV 6 เดือน (`pcv3_date`)

*(หมายเหตุ: คอลัมน์ HBV เข็ม 4 และ 6 เดือนสลับกันตามโครงสร้าง HOSxP — `hbv4_date` = เข็ม 4 เดือน, `hbv3_date` = เข็ม 6 เดือน)*
- **9 เดือน:** MMR 9 เดือน (`mmr1_date`)
*(หมายเหตุ: Rota ครบถ้วนตามเกณฑ์ จะพิจารณาจากชนิดวัคซีน หากเป็นชนิด 2 ครั้งเช็ค `rv21, rv22` หากเป็นชนิด 3 ครั้งเช็ค `rv31, rv32, rv33`)*
*(หมายเหตุ: หากอายุยังไม่ถึงเกณฑ์ เช่น อายุ 3 เดือน ระบบจะไม่แสดงผลว่าขาดวัคซีนของช่วง 4 เดือน)*

**มุมมองที่ 2: การประเมินเด็กอายุครบ 1 ปี (Fully Immunized) (อ้างอิง HDC Report 2)**
ใช้ประเมินเมื่อเด็กมีอายุครบ 1 ปีบริบูรณ์ ว่าได้รับวัคซีนพื้นฐานครบถ้วนหรือไม่ โดยเด็ก 1 คนจะผ่านเกณฑ์ "Fully Immunized" ก็ต่อเมื่อได้รับวัคซีนครบตามนี้:
- **BCG:** 1 ครั้ง (`bcg_date`)
- **HBV:** 4 ครั้ง (ต้องมีวันที่ครบทั้ง `hbv1_date` AND `hbv2_date` AND `hbv4_date` AND `hbv3_date` — แรกเกิด + 2 + 4 + 6 เดือน; คอลัมน์เข็ม 4/6 เดือนสลับตามโครงสร้าง HOSxP: `hbv4_date` = เข็ม 4 เดือน, `hbv3_date` = เข็ม 6 เดือน — ยืนยันโดยผู้ดำเนินการ 2026-10-30, Issue #74)
- **DTP:** 3 ครั้ง (เช็ค `dtp1_date` AND `dtp2_date` AND `dtp3_date` ต้องมีค่าครบทั้ง  3)
- **Hib:** 3 ครั้ง (เช็ค `hib1_date` AND `hib2_date` AND `hib3_date` ต้องมีค่าครบทั้ง 3)
- **IPV:** 2 ครั้ง (เช็ค `ipv1_date` AND `ipv2_date`)
- **OPV:** 1 ครั้ง (`opv3_date` — OPV 6 เดือน รหัส HDC 083) ตามสูตร 2 IPV + 3 OPV ที่ใช้ IPV แทน OPV ที่ 2/4 เดือนตั้งแต่ 1 ก.ค. 2566 (ที่มา: [research §3, §3.1](research/hdc-je-indicators-and-epi-schedule-2569.md)); `opv1_date`/`opv2_date` คือวัคซีนโปลิโอเข็มที่ 1/2 **ชนิดใดก็ได้** ไม่ใช่เฉพาะ OPV ([research §3.3](research/hdc-je-indicators-and-epi-schedule-2569.md)) จึงไม่มีกฎ `opv1_date`/`opv2_date` ใน seed ของกลุ่ม 1 และ 2 ปี — เด็กทั้งสองกลุ่มเกิดหลังวันเปลี่ยนสูตร และกฎนี้จะผ่านสำหรับเด็กที่ได้ IPV ทุกคน (Issue #121)
- **MMR:** 1 ครั้ง (`mmr1_date`)
- **Rota:** ครบถ้วนตามเกณฑ์ (มีข้อมูลครบ 2 เข็มใน `rv2` หรือครบ 3 เข็มใน `rv3`)
*(หากได้รับครบตามรายการด้านบน จะถือว่าผ่านเกณฑ์ Fully Immunized และนำไปคิดเป็นร้อยละความครอบคลุมภาพรวมของ รพ.สต.)*

**มุมมองที่ 1: การติดตามวัคซีนรายไตรมาส / รายช่วงอายุ (เด็ก 3 ปี)**
- **2 ปีครึ่ง - 3 ปี:** LAJE เข็ม 2 (`j12_date`)

**มุมมองที่ 2: การประเมินเด็กอายุครบ 3 ปี (Fully Immunized)**
ใช้ประเมินเมื่อเด็กมีอายุครบ 3 ปีบริบูรณ์ ว่าได้รับวัคซีนพื้นฐานครบถ้วนหรือไม่:
- **BCG:** 1 ครั้ง (`bcg_date`)
- **HBV:** 4 ครั้ง (`hbv1_date`, `hbv2_date`, `hbv4_date`, `hbv3_date`)
- **DTP:** 4 ครั้ง (`dtp1_date` ถึง `dtp4_date`)
- **Hib:** 3 ครั้ง (`hib1_date` ถึง `hib3_date`)
- **IPV:** 2 ครั้ง (`ipv1_date`, `ipv2_date`) สำหรับเด็กเกิดตั้งแต่ 1 พ.ค. 2566
- **โปลิโอ เข็ม 1/2 (สูตรเดิม):** สำหรับเด็กเกิดก่อน 1 พ.ค. 2566 แทน IPV เข็ม 1/2 — `opv1_date` และ `opv2_date` (วัคซีนโปลิโอชนิดใดก็ได้ที่ 2 และ 4 เดือน) ดูข้อ Birth Window ด้านล่าง
- **IPV 4 เดือน (สูตรเดิม):** สำหรับเด็กเกิดก่อน 1 พ.ค. 2566 — `ipv2_date` (IPV 1 เข็มของสูตรเดิม, Issue #152)
- **OPV:** 2 ครั้ง (`opv3_date` AND `opv4_date` สำหรับ 6 และ 18 เดือน) ตาม report template ข้อ 6
- **MMR:** 2 ครั้ง (`mmr1_date`, `mmr2_date`)
- **Rota:** ครบถ้วนตามเกณฑ์ (2 หรือ 3 ครั้ง)
- **LAJE:** 2 ครั้ง (`j11_date` AND `j12_date`)

เกณฑ์ JE ของกลุ่ม 3 ปีใช้ LAJE อย่างเดียว แม้ template ของ HDC ยังเขียนว่า "LAJE 2 ครั้ง หรือ JE 3 ครั้ง" เพราะไฟล์ HDC ไม่มีคอลัมน์ `je3_date` ในทุกกลุ่มอายุ (ทางเลือก JE 3 ครั้งจึงตัดสินไม่ได้ตลอด) และ JE เชื้อตายไม่อยู่ในตาราง EPI 2569 ซึ่งให้ LAJE 2 ครั้งที่ 1 ปีและ 2 ปี 6 เดือน ([research](research/hdc-je-indicators-and-epi-schedule-2569.md), Issue #127)

ค่าเริ่มต้นใน `seedVaccineRules` ใช้กรอบ report template ข้อ 6 ที่ได้รับสำหรับมุมมองที่ 2 อายุ 3 ปี โดยเด็กสูตรใหม่ต้องมี IPV ทั้งสองเข็ม ไม่มีทางเลือกให้ OPV ชดเชย IPV ส่วนเด็กสูตรเดิมใช้ชุดกฎสูตรเดิมตามข้อ Birth Window ด้านล่าง ส่วน HBV ใช้ครบ 4 เข็ม (`hbv1_date`, `hbv2_date`, `hbv4_date`, `hbv3_date` ตามลำดับอายุ 0/2/4/6 เดือนของโครงสร้าง HOSxP) — ผ่านการยืนยันของผู้ดำเนินการแล้ว (Issue #74)

**สรุป View 2 กับไฟล์ที่คอลัมน์ไม่ครบ (Issue #89):** การใช้กฎ V2 แต่ละข้อในการคำนวณสรุปมีความพร้อมของคอลัมน์ต้นทางเป็นเงื่อนไขขั้นแรก ผ่านประตูเดียวกับ View 1 (`ruleSourceDecidable`): ALL/ANY ต้องยืนยันคอลัมน์ `required_fields` ครบ และ BRANCH ต้องยืนยันครบทั้งสองทางเลือก (Issue #78) แถวเก่าที่ไม่มี manifest ใช้ค่าที่ไม่ว่างเป็นหลักฐานคอลัมน์แทน

- เด็กที่มีกฎ V2 ที่ยืนยันคอลัมน์ไม่ได้แม้ข้อเดียว และไม่มีเข็มที่ขาดจริง ตัดสิน Fully Immunized รายคนไม่ได้ ("ประเมินไม่ได้") ออกจากตัวหารความครอบคลุมและถูกนับแยกใน `view2NotEvaluableCount` — ไม่ถูกนับเป็น "ยังไม่ผ่านเกณฑ์" และไม่เข้ารายชื่อตามฉีดวัคซีน เพราะเป็นงานคุณภาพข้อมูล (ตามหาไฟล์ใหม่) ไม่ใช่การตามฉีด
- ยกเว้นเด็กที่กฎอื่นยืนยันได้ว่าขาดเข็มจริง (คอลัมน์มีแต่ไม่มีวันที่ และถึงอายุเป้าหมายแล้ว) ยังเป็น "ยังไม่ผ่านเกณฑ์" อยู่ในตัวหารและรายชื่อตามฉีด (รวมกรณีมี Pending Rule ร่วมด้วย — ดูข้อ View 2 Pending ด้านล่าง) ส่วนกฎที่ประเมินไม่ได้แสดงแยกรายกฎที่ตัวหาร 0 (Issue #103, ADR-0006)
- ลำดับความสำคัญ (Issue #101, #102, ADR-0006): Confirmed Missing Dose > ตรวจสอบประวัติ > Pending Rule > ประเมินไม่ได้ > ผ่าน ตัดสินจากกฎในระบบเท่านั้น `result` ของ HDC ไม่ย้ายเด็กระหว่างกลุ่ม ไม่ backfill กฎใดเข้ากลุ่มผ่าน และไม่สร้างรายการสรุปที่ไม่ใช่วัคซีนอีก — summary ที่บันทึกก่อน #101 อาจยังมี bucket คำตัดสิน HDC (`category: 'hdc_verdict'`, Issue #97) ซึ่ง reader ยังข้ามตามเดิมจนกว่าจะประมวลผลสรุปใหม่
- **View 2 Pending** (มี Pending Rule และไม่มี Confirmed Missing Dose) ออกจากตัวหารและนับแยกใน `view2PendingCount` ตามสัญญา #23 เด็กที่มี Confirmed Missing Dose เป็น "ยังไม่ผ่านเกณฑ์" อยู่ในตัวหารแม้มี Pending Rule ร่วมด้วย — แทนเงื่อนไข #23 AC5 ที่ตัดเด็กที่มี Pending Rule ใด ๆ ออกจากตัวหาร (Issue #119 ตามหลักการ ADR-0006 ที่ห้ามทำเด็กที่ขาดเข็มจริงหลุดการติดตาม) สรุปจัดกลุ่มจากสถานะรายคนของ engine จุดเดียว Pending Rule ไม่เข้าตัวหารรายกฎแม้เด็กอยู่ในตัวหาร View 2; สรุปที่สร้างใหม่แบ่งกลุ่มเป็นเอกภาพ `view2ApplicableTotal + view2PendingCount + view2NotEvaluableCount + view2ReviewCount = total` และแสดงตัวหารข้างร้อยละ View 2 เสมอ (ผ่าน X/Y คน พร้อมจำนวนข้อมูลไม่ครบและตรวจสอบประวัติแยก)
- ทางแก้เด็กกลุ่มประเมินไม่ได้คือนำเข้าไฟล์ที่มีคอลัมน์ครบอีกครั้ง (โหมดเติมข้อมูล — manifest แบบ union จะทำให้ประเมินได้ทันที) แล้วประมวลผลสรุปใหม่

**Birth Window และสูตรโปลิโอที่เปลี่ยนระหว่างรุ่น (Issue #121, [ADR-0008](adr/0008-vaccine-rule-birth-window-keyed-on-birth-date.md)):** กฎแต่ละข้อมีช่วงวันเกิดได้ (นิยาม Birth Window และ Inapplicable Rule ดู `CONTEXT.md` §41–§42, สัญญาการเก็บดู [`schema.md`](schema.md) `vaccine_rules`) ส่วนนี้กำหนดวิธีที่ engine ใช้

- engine ตัดสินช่วงวันเกิดก่อนการตรวจคอลัมน์ วันที่ และอายุเป้าหมาย เทียบแบบวันปฏิทิน `เกิดตั้งแต่ <= วันเกิด < เกิดก่อน` ใช้กับ View 1, View 2 และสรุปเหมือนกัน
- เด็กที่เกิดนอกช่วงของกฎ: กฎนั้นเป็น Inapplicable Rule ไม่เข้าตัวหารรายกฎ ไม่เตือนคอลัมน์ขาดหรือวันที่ผิดปกติ ไม่อยู่ในรายชื่อตามฉีดและ breakdown แต่แสดงในประวัติวัคซีนว่า "ไม่ใช้กับเด็กรายนี้ (เกิดก่อน/ตั้งแต่ <วันที่ พ.ศ.>)" เด็กที่กฎที่ยังไม่ครบมีแต่ Inapplicable Rule ถูกประเมินจากกฎที่เหลือ
- เด็กที่ไม่มีวันเกิดที่ถูกต้อง: กฎที่มีช่วงเป็น "ประเมินไม่ได้" (ถังเดียวกับคอลัมน์ไม่ครบ #89) เพื่อให้แก้ข้อมูลต้นทาง ไม่ใช่ตามฉีดสองสูตรพร้อมกัน ลำดับ #103 คงเดิม: เด็กที่ขาดเข็มจริงจากกฎอื่นยังเป็น "ยังไม่ผ่านเกณฑ์"
- ค่าช่วงวันเกิดในชีตที่ไม่ใช่วันที่ (เช่นพิมพ์ลงชีตตรงโดยไม่ผ่านหน้า Rules Engine): กฎนั้นเป็น "ประเมินไม่ได้" สำหรับทุกคน ไม่ถือว่าไม่มีช่วง (fail closed) — แก้ค่าในหน้า Rules Engine
- สูตรโปลิโอ: เปลี่ยนจาก OPV 2/4 เดือนเป็น IPV 2/4 เดือนตั้งแต่ 1 ก.ค. 2566 ([research §3.1](research/hdc-je-indicators-and-epi-schedule-2569.md)) วันตัดคือวันเกิด **1 พ.ค. 2566 (2023-05-01)** เด็กเกิดก่อนวันนี้ครบ 2 เดือนก่อนวันเปลี่ยนสูตร กลุ่มอายุที่คร่อมวันตัดตั้งเป็นสองชุดกฎที่ใช้วันตัดเดียวกัน
  - **IPV เข็ม 1/2:** เกิดตั้งแต่ 2023-05-01 — เด็กหลังวันตัดที่ได้ OPV แทน IPV ยังขาด IPV (ตามฉีด IPV ตามปฏิทิน 2569)
  - **โปลิโอ เข็ม 1/2 (สูตรเดิม):** เกิดก่อน 2023-05-01 ใช้ `opv1_date`/`opv2_date` อายุเป้าหมาย 2/4 เดือน วัคซีนโปลิโอชนิดใดก็ได้ที่ 2/4 เดือนผ่านกฎนี้
  - **IPV 4 เดือน (สูตรเดิม):** เกิดก่อน 2023-05-01 ใช้ `ipv2_date` อายุเป้าหมาย 4 เดือน — สูตรเดิมมี IPV 1 เข็มที่ 4 เดือน และ HDC เก็บเข็มนี้ใน `ipv2_date` ด้วยรหัส I12/D32/D42/D52 ไม่นับ IPV-P (รหัส 401) (Issue #152, [research §2.5](research/hdc-je-indicators-and-epi-schedule-2569.md))
  - เด็กที่ไม่เคยได้รับวัคซีนยังอยู่ในรายชื่อตามฉีดตามสูตรที่วันเกิดเลือก
  - seed ตั้งค่าเช่นนี้ให้กลุ่ม 3 และ 5 ปี (มุมมองที่ 2) พร้อมหมายเหตุให้ลบกฎสูตรเดิมเมื่อกลุ่มอายุไม่มีเด็กเกิดก่อนวันตัดแล้ว (3 ปี ตั้งแต่ปีงบ 2570, 5 ปี ตั้งแต่ปีงบ 2572) การ clone ปีคัดลอกช่วงวันเกิดเดิมทุกกฎ กฎสูตรเดิมมี `metric_key` ของตัวเอง ไม่เชื่อมกับ IPV เข็ม 1/2
  - HDC เลือกสูตรโปลิโอตามกลุ่มอายุ ไม่ใช่ตามวันเกิด (Polio Regimen, `CONTEXT.md` §49): กลุ่ม 5 ปีนับเฉพาะ IPV 4 เดือน ส่วนกลุ่ม 3 ปีบังคับ IPV 2 เข็มกับเด็กทุกคน เด็ก 3 ปีสูตรเดิมที่มีเฉพาะ `ipv2_date` จึงผ่านตามกฎแต่ HDC `ไม่ผ่าน` และติดป้าย "ผลไม่ตรงกับ HDC" — เป็นความต่างของเกณฑ์ ไม่ใช่เข็มที่ขาด (Issue #126, หลักฐานดู [research §2.5](research/hdc-je-indicators-and-epi-schedule-2569.md))
- ตัวหารรายกฎลดลงเหลือเด็กที่กฎใช้ได้ สรุปที่เก็บไว้เปลี่ยนตามหลังประมวลผลสรุปใหม่เท่านั้น

Template ยังไม่ได้แจกแจงเงื่อนไขวันที่ซ้ำ/ระยะห่างหรือสูตรผสม จึงไม่เพิ่มข้อสันนิษฐานเหล่านี้ใน seed ผลผ่าน/ไม่ผ่านตัดสินจากกฎที่เจ้าหน้าที่ตั้งค่า (#101); การแก้ seed นี้ไม่เปลี่ยนตัวตรวจวันที่ใน engine ปัจจุบัน การทดลองเฉพาะความครบของคอลัมน์กับข้อมูล active 232 แถวให้ผลตรง 231 แถว โดยอีก 1 แถวยังอธิบายสาเหตุไม่ได้แน่ชัด

การแก้ค่าเริ่มต้นไม่อัปเดต `vaccine_rules` ที่มีอยู่โดยอัตโนมัติ และ `seedVaccineRules(..., ..., true)` จะ reset ทุกกลุ่มอายุของปีที่เลือก จึงไม่ใช่คำสั่งอัปเดตเฉพาะกลุ่ม 3 ปี

> **หมายเหตุ:** มุมมองที่ 1 และ 2 ประมวลผลจาก **ข้อมูลรายบุคคล (Excel Upload)** เท่านั้น แยกจากข้อมูลรวม HDC OpenData ที่จัดเก็บใน Backend cache

- แสดงกราฟ (Bar Chart/Pie Chart) ร้อยละความครอบคลุม (Coverage Rate) เปรียบเทียบผลงานของแต่ละ รพ.สต.
- หน้า `/dashboard` มีตัวเลือกปีงบประมาณและไตรมาส โดย **ค่าเริ่มต้นต้องเป็นปีงบประมาณปัจจุบันตามปฏิทินไทย** (ตุลาคมเริ่มปีงบประมาณถัดไป) แม้จะยังไม่มีสรุปของปีปัจจุบัน ตัวเลือกปีต้องมีปีปัจจุบันเสมอ และเพิ่มปีอื่น ๆ จาก union ของปีที่มีสรุปประจำปีใช้งานได้จริงใน `Dashboard_Summaries` ของเด็กอายุ 1, 2, 3 และ 5 ปี ผ่าน `getDashboardSummaryYears` ไม่ใช้ปีของ Rules Engine ที่ยังไม่มี summary และไม่เปลี่ยนกลับไปปีล่าสุดที่มีข้อมูลเอง ผู้ใช้สามารถเลือกปีเก่าได้ และเมื่อเปลี่ยนปีจะกลับไปมุมมองทั้งปีงบประมาณก่อน
- ปีและไตรมาสที่เลือกใช้ร่วมกับการดึง summary และเป้าหมาย View 1 / View 2 ของทั้งสี่กลุ่มอายุ หากบางกลุ่มหรือบางไตรมาสไม่มีสรุปให้แสดง `ไม่มีข้อมูลสรุป` ไม่แปลงเป็น 0; ค่า 0 ที่บันทึกจริงยังต้องแสดงตามจริง แยกสถานะกำลังโหลด/ข้อผิดพลาด API ของสรุปและรายการปีย้อนหลัง/ไม่มีข้อมูลของปีที่เลือกอย่างชัดเจน ไม่ให้ความล้มเหลวของรายการปีย้อนหลังปิดบังสรุปของปีปัจจุบัน และไม่มีการคำนวณหรือเขียนข้อมูลย้อนหลังอัตโนมัติ


- หน้า `/dashboard` → เด็กอายุครบ 1, 2, 3 และ 5 ปี → รายละเอียด View 1 (ภาพรวมทั้งปี) มีปุ่มพับ/ขยาย **เปรียบเทียบกับ HDC OpenData** ซึ่งอ่านข้อมูลรวม `s_epi1/2/3/5` ผ่าน `getOpenData` เฉพาะเมื่อเปิด โดยให้รายชื่อวัคซีนมาจาก `vaccine_rules`/`Dashboard_Summaries` ตามปีและอายุจริง ใช้ crosswalk ที่ยืนยันรหัส/คอลัมน์แล้วเพื่ออ้างอิงตัวชี้วัดจาก HDC เท่านั้น กฎ EPI, คะแนน View 1/2, เป้าหมาย และข้อมูลรายบุคคลไม่เปลี่ยน หากตัวตั้ง/ตัวหาร รายงานหรือรหัสวัคซีนเทียบไม่ได้จะไม่สร้างส่วนต่างเทียม รายละเอียดดู [HDC OpenData comparison](hdc-opendata-comparison.md)
- หน้า `/dashboard` → **View 1 (รายวัคซีน)** เป็นจุดเดียวสำหรับดูและเปรียบเทียบ HDC OpenData รายเข็ม; **View 2 (ครบชุด)** แสดงผล Fully Immunized ตามกฎ/สถานะ EPI และผลรายหน่วยบริการ โดยไม่แสดง HDC รายเข็มซ้ำหรือเพิ่มส่วนเปรียบเทียบอีกชุด ([ข้อกำหนด](hdc-opendata-comparison.md))

**แนวทางข้อความบน Dashboard:** ใช้ชื่อ "รายวัคซีน" ใน View 1 และ "ครบชุด" ใน View 2 ให้สอดคล้องกับแท็บและการ์ด ใช้ "ผ่านเกณฑ์/ยังไม่ผ่านเกณฑ์" สำหรับผลประเมินรายคนหรือรายเข็ม หลีกเลี่ยงคำว่า "ตกหล่น" เพราะจำนวนที่ยังไม่ผ่านเกณฑ์ไม่ยืนยันว่าเด็กไม่ได้รับวัคซีนจริง ใช้ "ถึงเป้าหมาย/ต่ำกว่าเป้าหมาย" เฉพาะเมื่อกำหนดค่าเป้าหมายไว้แล้ว และใช้ "ยังไม่กำหนดเป้า" เมื่อไม่มีเกณฑ์เปรียบเทียบ ไม่แสดง PASS/FAIL ที่อาจทำให้เข้าใจผิด อธิบาย View 2 ว่าเป็นผลประเมินรายคนตามกฎที่ตั้งค่าไว้ ไม่ใช่ค่าเฉลี่ยรายเข็ม และผล HDC ที่นำเข้าเป็นข้อมูลประกอบ (Issue #101) ข้อความ HDC ใน View 1 ต้องชี้แจงแหล่งข้อมูลและข้อจำกัดเมื่อจำนวนที่ใช้คำนวณต่างกัน โดยไม่เปลี่ยนความหมายหรือสูตรของตัวเลข แสดงตัวหารข้างร้อยละ View 2 เสมอ ("ผ่าน X/Y คน") และใช้ "ข้อมูลไม่ครบ/ประเมินไม่ได้" แยกจาก "ยังไม่ผ่านเกณฑ์" เพราะเป็นคนละกลุ่มปัญหา (คุณภาพข้อมูล ไม่ใช่การตามฉีด — Issue #89)

### 3.6 การตรวจข้อมูลวันที่จาก Vaccine Rules Engine

ผู้ดูแลแก้แต่ละเกณฑ์ เลือกอนุญาตตรงวันเกิด/เตือนก่อนวันเกิด เพิ่มหรือลบคู่เข็มห้ามวันซ้ำ และคู่ลำดับวันที่ จากนั้นบันทึกฉบับร่างและยืนยันบันทึกตามขั้นตอนเดิม หน้าทบทวนแสดงความเปลี่ยนแปลงด้วยชื่อเข็ม

**เพิ่มและลบเกณฑ์ (Issue #148):** ผู้ดูแลเพิ่มหรือลบ Vaccine Rule ของปีงบประมาณและกลุ่มอายุที่เลือกได้ ทั้งสองอย่างเข้าฉบับร่างและผ่านหน้าทบทวนแล้วยืนยัน Batch Save พร้อมกับการแก้ไข ความต่างของปิดใช้งานกับลบดู [`CONTEXT.md` §19](../CONTEXT.md)

- ปุ่ม "เพิ่มเกณฑ์" แสดงเฉพาะเมื่อกลุ่มอายุนั้นมีกฎอยู่แล้ว ปีที่ยังไม่มีกฎเริ่มจาก seed หรือคัดลอกปี
- เกณฑ์ใหม่เริ่มจากฟอร์มว่าง `rule_id` เป็น UUID และ `is_required_for_v2` เปิดเป็นค่าเริ่มต้น ตัวตนข้ามปีของเกณฑ์ใหม่เป็นไปตาม [Decision E](specs/comparison-page-improvement.md) ไม่อนุมานจากชื่อ
- อายุเป้าหมายบังคับกรอกสำหรับเกณฑ์ใหม่ ระบบเติมค่าจาก `suggestRuleTargetAges` (แหล่งเดียว `TARGET_AGE_MONTHS_BY_FIELD`) เมื่อรู้จักคอลัมน์ เกณฑ์เดิมยังไม่บังคับ
- การตรวจวันที่ของเกณฑ์ใหม่เติมด้วยตรรกะเดียวกับกฎที่ยังไม่มีการตั้งค่า (#100) จากกฎในฉบับร่างของกลุ่มอายุนั้น ค่าเปลี่ยนตามคอลัมน์และอายุเป้าหมายจนกว่าผู้ดูแลจะแก้ส่วนนี้เอง และบันทึกเป็นค่าชัดเจนเสมอ
- คอลัมน์ที่ไม่มีกฎอื่นของกลุ่มอายุใช้ แสดงคำเตือนให้ตรวจชื่อกับไฟล์นำเข้า (มิฉะนั้นกฎประเมินไม่ได้กับเด็กทุกคน) คำเตือนไม่บล็อกการบันทึก
- ปุ่มลบทำเครื่องหมาย "จะถูกลบ" ในฉบับร่าง ยกเลิกได้ก่อน Batch Save ลบกฎสุดท้ายที่เหลือของกลุ่มอายุไม่ได้ (ให้ปิดใช้งานแทน)
- หน้าทบทวนแยกสามกลุ่ม: แก้ไข, "เพิ่มใหม่" (แสดงทุกช่องของเกณฑ์ใหม่) และ "ลบ" ซึ่งเตือนว่าความต่อเนื่องข้ามปีของตัวชี้วัดสิ้นสุด และแนะนำให้ปิดใช้งานถ้าต้องการหยุดชั่วคราว
- ผลสรุป Dashboard ที่บันทึกแล้วไม่เปลี่ยน หลังบันทึกระบบแนะนำให้ประมวลผลสรุปใหม่ตามเดิม

**ชื่อเข็ม (Issue #130):** ข้อสังเกตวันที่ ตัวเลือกคู่เข็ม และหน้าทบทวนของ Rules Engine ใช้ชื่อเข็มเดียวกัน ชื่อของคอลัมน์คือ `display_name` ของกฎแรก (ตามลำดับกฎของปีงบประมาณและกลุ่มอายุ ทั้ง View 1 และ View 2 — มุมมองที่ 1 ตรวจเฉพาะกฎของกลุ่มอายุแต่ตั้งชื่อจากกฎชุดเดียวกันนี้) ที่ใช้คอลัมน์นั้นคอลัมน์เดียว (ฟิลด์บังคับรวมฟิลด์ทางเลือกคือคอลัมน์นั้นเท่านั้น) ถ้าไม่มีกฎเช่นนั้นใช้ชื่อตามคอลัมน์ เช่น “Rota ชนิด 2 เข็ม — เข็ม 2”, “JE เข็ม 1”, “LAJE เข็ม 1”, “DTP เข็ม 2” เพราะกฎหลายคอลัมน์ เช่น “Rota (ครบถ้วนตามเกณฑ์)” หรือ “LAJE/JE 1 ปี” ไม่ได้บอกว่าเป็นเข็มไหน

**ข้อความข้อสังเกตวันที่ (Issue #130):** วันที่ใช้รูปแบบเดียวกับตารางประวัติ (DD-MM-YYYY วันปฏิทินไทย) ค่าที่รูปแบบผิดแสดงตามที่บันทึกในเครื่องหมายคำพูด

| ชนิด | ข้อความ |
|---|---|
| คู่ห้ามวันซ้ำ | DTP เข็ม 2 และ DTP เข็ม 3 ฉีดวันเดียวกัน (03-05-2024) |
| คู่ลำดับสลับ | DTP เข็ม 3 (03-05-2024) ฉีดก่อน DTP เข็ม 2 (10-06-2024) |
| ก่อนวันเกิด | BCG ฉีดก่อนวันเกิด (14-01-2025, เกิด 15-01-2025) |
| ตรงวันเกิดที่กฎไม่อนุญาต | DTP เข็ม 1 ฉีดตรงวันเกิด (15-01-2025) ซึ่งเกณฑ์ไม่อนุญาต |
| รูปแบบวันที่ผิด | OPV เข็ม 3 รูปแบบวันที่ไม่ถูกต้อง ("01/05/2567") |

ข้อสังเกตของเด็กหนึ่งรายไม่ซ้ำกันตามชนิดและคอลัมน์ คู่ห้ามวันซ้ำที่ตั้งไว้ในสองกฎ (หรือสลับข้าง) จึงเป็นข้อสังเกตเดียว และเข็มที่ผิดการตรวจเดียวกันในหลายกฎแสดงครั้งเดียว ข้อความที่แสดงไม่เปลี่ยนผลตามกฎ สถานะ หรือตัวเลขสรุปของ #102 การแสดงในรายชื่อ ไฟล์ส่งออก และประวัติดู [hdc-record-display](hdc-record-display.md)

การตั้งค่าวันที่มีขอบเขตตามกฎ ปีงบประมาณ และกลุ่มอายุที่เลือก

**สถานะ "ตรวจสอบประวัติ" (Issue #102, [ADR-0006](adr/0006-vaccine-rules-sheet-is-staff-owned-primary-source.md) ข้อ 4):** คำเตือนวันที่ (ก่อนวันเกิด ตรงวันเกิดที่กฎไม่อนุญาต วันซ้ำในคู่ห้ามซ้ำ ลำดับสลับ รูปแบบวันที่ผิด) ไม่ใช่เข็มขาด engine ตัดสินแต่ละกฎตามลำดับนี้ (View 1 และ View 2 เหมือนกัน)

- ดูวันที่ครบตาม ALL/ANY/BRANCH ก่อน — เซลล์ว่างหรือขีดคือไม่มีวันที่ กฎนั้นเป็นขาด (Confirmed Missing Dose) หรือ Pending Rule ตามอายุเป้าหมาย แม้กฎเดียวกันมีคำเตือนวันที่ร่วมด้วย ค่าที่ไม่ว่างแต่รูปแบบผิดนับว่ามีวันที่
- วันที่ครบแต่มีคำเตือน → กฎนั้นเป็น "ตรวจสอบประวัติ" ไม่ผ่านและไม่ขาด คำเตือนบนวันที่ใดของกฎก็นับ รวมทางเลือกที่ไม่ได้ใช้ของ BRANCH และเข็มอื่นของ ANY เพื่อให้ข้อมูลที่ผิดขึ้นในรายการงานคุณภาพข้อมูล (เจ้าของระบบ 2026-11-12)
- View 2: เด็กที่ไม่มีเข็มขาดจริงแต่มีกฎตรวจสอบประวัติอย่างน้อยหนึ่งข้อ เป็นสถานะ "ตรวจสอบประวัติ" (ลำดับดู §3.1) ออกจากตัวหารความครอบคลุมและตัวหารรายกฎทุกข้อ (แบบเดียวกับ View 2 Pending และประเมินไม่ได้) นับแยกใน `view2ReviewCount` ไม่ใช่คำตัดสินผ่าน/ไม่ผ่าน จึงไม่ติดป้าย "ผลไม่ตรงกับ HDC" เด็กที่ขาดเข็มจริงยังเป็น "ยังไม่ผ่านเกณฑ์" ส่วนกฎตรวจสอบประวัติของเด็กนั้นแสดงรายกฎที่ตัวหาร 0 แบบเดียวกับกฎที่ประเมินไม่ได้
- View 1: กฎรายเข็มที่ตรวจสอบประวัติไม่อยู่ในตัวหารร้อยละรายเข็มและรายวัคซีน นับแยกใน `view1ReviewDoses` รายชื่อแสดงสถานะ "ตรวจสอบประวัติ" (ลำดับในรายชื่อ: ข้อมูลไม่พอประเมิน > ไม่ครบ > ตรวจสอบประวัติ > ยังไม่ถึงเกณฑ์ > ครบ)
- รายชื่อตามฉีดคือรายการที่กรอง "ไม่ผ่าน"/"ไม่ครบ" จึงไม่รวมกลุ่มนี้ รายการงานคุณภาพข้อมูลคือรายการที่กรอง "ตรวจสอบประวัติ" ซึ่งไฟล์ส่งออกมีข้อสังเกตวันที่ให้แก้ข้อมูลต้นทางได้ (View 2 คอลัมน์ "ข้อสังเกตวันที่", View 1 อยู่ใน "รายละเอียดผล") ส่วนประวัติวัคซีนแสดงข้อสังเกตทั้งหมดพร้อมคำอธิบายว่าไม่นับเป็นวัคซีนขาด
- สรุปที่บันทึกก่อน #102 ยังนับคำเตือนวันที่เป็นเข็มขาดและไม่มีสองฟิลด์นี้ ต้องประมวลผลสรุปใหม่

Rota ในข้อมูลระบบมีชุดคอลัมน์ 2 เข็ม (`rv21`, `rv22`) และ 3 เข็ม (`rv31`, `rv32`, `rv33`); “Rota เข็ม 1” เป็นเกณฑ์เข็มแรก ส่วน “Rota (ครบถ้วน)” เป็นเกณฑ์ความครบชุด ไม่ใช่ชื่อผลิตภัณฑ์สองชนิด ตัวตรวจค่าเริ่มต้นไม่จับวันซ้ำข้ามสองชุดนี้

### 3.7 การเปรียบเทียบข้ามปีงบประมาณ (Year Comparison)

- สรุปประจำปีของแต่ละกลุ่มอายุอ่านจาก `Dashboard_Summaries` โดย **backend เป็นผู้ตัดสินลำดับความสำคัญของแถว**: ใช้แถว `<ตาราง>_<ปี>_all` ก่อน และใช้แถวรุ่นเดิม `<ตาราง>_<ปี>` เฉพาะเมื่อไม่มีแถว `_all` ของปี/ตารางนั้น — ส่งกลับแถวเดียวต่อ (ตาราง, ปี) เท่านั้น ฝั่งหน้าเว็บไม่เลือกเองด้วยเวลา `updated_at`
- ปีงบประมาณที่เสนอให้เปรียบเทียบมาจาก **ปีที่มีสรุปประจำปีใช้งานได้** (แยก `summaryData` เป็น JSON ได้และมี `total`/`view2Coverage`/`view2Passed` เป็นตัวเลข) ของแต่ละกลุ่มอายุทั้งสี่ (1, 2, 3 และ 5 ปี) แล้วรวมชุดปีงบประมาณที่มีข้อมูลจริงของอย่างน้อยหนึ่งกลุ่มอายุเป็นตัวเลือกปีระดับหน้า ไม่ใช้ปีจากการตั้งค่าทั่วไปหรือปีที่มีเพียงกฎวัคซีน
- ปีที่ไม่มีสรุปแสดงเป็น “ไม่มีข้อมูลสรุป” — **ไม่แปลงเป็น 0% หรือ 0 คน** ส่วนค่า 0 ที่เป็นข้อมูลจริงยังแสดง 0 ตามปกติ
- หน้า `/dashboard/comparison` แสดงผลสี่กลุ่มอายุ **1, 2, 3 และ 5 ปีพร้อมกัน** เป็น Dashboard เปรียบเทียบรายปีงบประมาณ โดยมีกราฟ **View 1 (รายโดส)** และ **View 2 (รายคน)** แยกจากกันในแต่ละกลุ่มอายุ; View 1 ไม่ใช้ตัวหารหรือค่า View 2 แทนกันและไม่รวมเป็นอนุกรมเดียวกัน
- **ตัวเลือกปีงบประมาณหนึ่งชุดใช้ร่วมกันทั้งสี่กลุ่มอายุ** โดยใช้ union ของปีที่มีสรุปประจำปีใช้งานได้ในแต่ละกลุ่ม ค่าเริ่มต้นเป็น 2 ปีล่าสุดของชุดนี้ (มีปีเดียวก็ใช้ปีนั้น) เลือกได้ **สูงสุด 5 ปี** และผู้ใช้ปลดเลือกทุกปีได้โดยไม่ถูกเลือกใหม่อัตโนมัติ ระหว่างปีที่กลุ่มอายุใดไม่มีสรุป ให้กลุ่มอายุนั้นแสดง “ไม่มีข้อมูลสรุป” ไม่บังคับว่าทุกกลุ่มอายุต้องมีข้อมูลในปีที่เลือก
- แต่ละปีงบประมาณเป็น **สรุปประจำปีที่จัดเก็บไว้ (snapshot) ณ เวลาที่คำนวณของปีนั้น** เวลา `updated_at` คือเวลาคำนวณ/บันทึกสรุป (แสดงเป็น “ข้อมูลสรุป ณ วันที่ …”) ไม่ใช่เวลาอัปโหลดข้อมูลต้นทาง และแต่ละปีอาจมีเวลาคำนวณต่างกัน — ไม่ใช่การคำนวณใหม่ ณ วันเดียวกัน
- กราฟรายปีใช้ความครอบคลุมจากสรุปที่จัดเก็บไว้จริง โดย View 1 ใช้ `view1Coverage` พร้อมจำนวนโดสที่ผ่าน/จำนวนโดสเข้าเกณฑ์ และ View 2 ใช้ `view2Coverage` พร้อมจำนวนเด็กผ่าน/เด็กเข้าเกณฑ์ประเมินที่มีข้อมูลจริง **ตัวหารเป็นศูนย์** ของสัญญาปัจจุบันให้แสดง “ยังประเมินไม่ได้” ไม่ใช่ 0% ส่วนสรุปรุ่นเดิมที่ไม่มีตัวหารจะไม่อนุมานตัวหารให้เอง
- ข้อความเปลี่ยนแปลงระหว่างปีเปรียบเทียบ **กลุ่มอายุเดียวกันและมุมมองเดียวกัน** กับปีที่เลือกก่อนหน้าซึ่งมีข้อมูลจริง ระบุปีฐานและใช้หน่วย “จุดร้อยละ” เป็นภาษาไทย (ไม่ใช้ `pp` เป็นข้อความหลัก) มีเพียงปีเดียวจะไม่แสดงค่าการเปลี่ยนแปลงข้ามปี
- เป้าหมายรายปีอ่านผ่าน `useTargetSettings` ด้วยไตรมาส `'all'` (แปลงเป็นเป้าหมาย Q4 ของปีนั้น) — ปีที่ไม่ได้กำหนดเป้าหมายแสดง “ไม่ได้กำหนดเป้าหมาย” **ไม่ใช้เป้าหมาย 0 แทน**
- สรุปรุ่นสัญญาปัจจุบัน (มี `view2ApplicableTotal` และ `view2PendingCount` เป็นตัวเลข) แสดงองค์ประกอบ **ผ่านเกณฑ์ / ไม่ผ่านเกณฑ์ / ยังไม่เข้าเกณฑ์ประเมิน / ประเมินไม่ได้ (ข้อมูลไม่ครบ) / ตรวจสอบประวัติ (วันที่ผิดปกติ)** โดย “ไม่ผ่านเกณฑ์” คำนวณ ณ ตอนแสดงผลจาก `view2ApplicableTotal − view2Passed` เท่านั้น (ไม่ได้เก็บในสรุป และไม่ใช้ `total − passed`) ส่วน “ประเมินไม่ได้” อ่านจาก `view2NotEvaluableCount` ที่บันทึกตั้งแต่ Issue #89 — สรุปที่สร้างก่อนหน้าไม่มีฟิลด์นี้ แสดง “—“ ไม่เติม 0 และ “ตรวจสอบประวัติ” อ่านจาก `view2ReviewCount` ที่บันทึกตั้งแต่ Issue #102 ในลักษณะเดียวกัน
- สรุปรุ่นเดิม (legacy) ยังแสดงความครอบคลุมและจำนวนผ่านเกณฑ์ แต่**รายละเอียดที่ต้องอาศัยตัวส่วน (เข้าเกณฑ์ประเมิน / ไม่ผ่านเกณฑ์ / ยังไม่เข้าเกณฑ์ประเมิน) ไม่สามารถแสดงได้** แสดงเป็น “—” พร้อมข้อความแจ้งว่า “ไม่มีข้อมูลรายละเอียดสำหรับ summary รุ่นนี้” — ไม่เติมค่า 0 หรืออนุมานตัวส่วนแทน
- สถานะต่าง ๆ แยกกันชัดเจน: ข้อผิดพลาด API ปีที่ใช้ได้ / ข้อผิดพลาด API สรุป / ข้อผิดพลาดการตั้งค่าเป้าหมาย (แสดงเป็นข้อผิดพลาด ไม่ใช่ “ไม่มีข้อมูล”) เมื่อ **ทั้งสี่กลุ่มอายุ** ไม่มีปีใช้งานได้จะแสดงสถานะไม่มีข้อมูลระดับหน้า และเมื่อปลดเลือกทุกปีจะแจ้งให้เลือกอย่างน้อย 1 ปี พร้อมไม่ส่งคำขอดึงสรุปด้วยรายการปีว่าง
- **การ์ดเจาะลึกผลการดำเนินงานรายปีงบประมาณ** เป็นส่วนขยายที่ผู้ใช้เปิดเองเพื่อวิเคราะห์ **รายการเดียวกันภายในมุมมองเดียวกันข้ามปี** และใช้ปีงบประมาณที่เลือกชุดเดียวกับกราฟภาพรวม โดยมีตัวเลือก 3 แกนคือ **กลุ่มอายุ 1/2/3/5 ปี → View 1 รายโดส หรือ View 2 รายคน → รายหน่วยบริการหรือรายวัคซีน**; ไม่คำนวณหรือสื่อความหมายว่าเป็นการลบ View 1 ด้วย View 2
- แสดงรายการหน่วยบริการ/วัคซีนเรียงตามร้อยละความครอบคลุมของปีล่าสุดที่ผู้ใช้เลือกจาก **น้อยไปมาก** โดยค่าที่ขาดหายหรือประเมินไม่ได้อยู่ท้ายและไม่ถือเป็นศูนย์ ผู้ใช้เลือกหนึ่งรายการเพื่อดูกราฟรายปีและค่าความครอบคลุม จำนวนผ่านเกณฑ์/จำนวนเข้าเกณฑ์ (หน่วยโดสหรือคนตรงตาม View) เป้าหมายประจำปี เวลาคำนวณสรุป และการเปลี่ยนแปลงจากปีที่มีข้อมูลเปรียบเทียบก่อนหน้า; ตารางตัวเลขแยกเป็นส่วนกดขยายภายหลัง
- ข้อมูลรายหน่วยบริการอ่านจาก `facilityBreakdownV1` หรือ `facilityBreakdownV2` ของ View ที่เลือกเท่านั้นและเชื่อมข้ามปีด้วย **`hoscode` สตริงตามที่จัดเก็บ** (เช่น `06413` ต่างจาก `6413`) ชื่อที่เปลี่ยนไม่สร้างหน่วยใหม่หรือรวมคนละหน่วย; ข้อมูลรายวัคซีนอ่านจาก `view1Breakdown` หรือ `view2Breakdown` และเชื่อมด้วย **`metric_key`** ภายในกลุ่มอายุและ View เดียวกัน ชื่อวัคซีนเป็นเพียงข้อความแสดงผล ส่วนรายวัคซีนรุ่นเดิมที่ไม่มีรหัสเชื่อมโยงต้องแจ้งเป็นจำนวนที่วัดจริงตามกลุ่มอายุ+มุมมอง+ปีที่เลือก (เช่น "ปี 2569 · View 2: ข้อมูลสรุปมีวัคซีน 3 รายการ โดย 1 รายการยังไม่มีรหัสเชื่อมโยงสำหรับการเปรียบเทียบข้ามปี (อีก 2 รายการเปรียบเทียบได้)" — ครบทุกรายการให้ใช้คำว่าทุกรายการ) ไม่ใช่ข้อความรวมทั้งปี; bucket คำตัดสิน HDC (`category: 'hdc_verdict'`) ไม่ใช่วัคซีน จึงไม่ถูกนับเป็นรายการไร้รหัสและไม่ก่อการเตือน (Issue #97)
- การเปลี่ยนแปลงจากปีก่อนใช้ **ความครอบคลุมของปีปัจจุบันลบด้วยความครอบคลุมของปีที่เลือกก่อนหน้าซึ่งมีค่าที่ประเมินได้จริง** ของหน่วย/วัคซีน กลุ่มอายุและ View เดียวกัน (หน่วย **จุดร้อยละ** พร้อมระบุปีฐาน) ไม่อนุมานจากปีที่ไม่มีข้อมูลหรือใช้เปรียบเทียบข้าม View ส่วนต่างจากเป้าหมายเป็นอีกค่า คือความครอบคลุมของปีนั้นลบเป้าหมายของ View/ปี/กลุ่มวัคซีนที่เกี่ยวข้องผ่าน `getTarget('all', view, vaccineGroup?, fiscalYear)`; ไม่กำหนดเป้าหมายให้แสดง “ไม่ได้กำหนดเป้าหมาย” และค่าเป้าหมาย 0 ที่กำหนดจริงต้องยังคงแสดงเป็น 0
- รายละเอียดใช้ **สรุปประจำปีที่จัดเก็บไว้เท่านั้น** ไม่ดึงรายบุคคลหรือ OpenData ใหม่ และไม่ประเมินวัคซีนใหม่ ปีที่ไม่มีสรุป, รายการที่ขาดในสรุป, สรุปเก่าที่ขาดทั้ง breakdown, รายการที่ตัวหารเป็น 0, ค่าไม่ถูกต้อง และค่า 0% จริงที่มีตัวหารเป็นบวก ต้องแสดงเป็นสถานะที่ไม่ปะปนกัน ไม่มีการเติมค่าที่ไม่ได้บันทึก เวลาของแต่ละปีระบุ **ข้อมูลสรุป ณ วันที่** ไม่ใช่เวลาอัปโหลด
