# HDC column upgrade — 1, 2, 3 และ 5 ปี

## ขอบเขตและสัญญาข้อมูล

`getEpiSchemas()` เป็น schema ฝั่ง GAS; `hdcSourceFields()` เป็น allowlist ฝั่งนำเข้า มี contract test เทียบให้ตรงกันทุกอายุ เก็บ `addr`, `check_typearea`, `nation`, `discharge`, `g_hbv`, `g_dtp`, `g_hib`, `g_opv`, `g_mmr`, `g_rv`, `g_pcv` และคู่ `*_hospcode` / `*_input_hosp` สำหรับทุกคอลัมน์วัคซีนเดิม

- `check_typearea` คือชื่อจริง ยอมรับ `heck_typearea` เป็น alias เฉพาะตอนอ่านไฟล์
- `hoscode` หมายถึงหน่วยรับผิดชอบบุคคล ไม่ถูกแทนที่ด้วยหน่วยที่ฉีดหรือหน่วยบันทึก
- รหัสหน่วยฉีด/หน่วยบันทึกเก็บเป็นข้อความ 5 ตำแหน่ง รองรับอักษรและตัวเลขตามไฟล์ตัวอย่าง เช่นรหัสรูปแบบ `AE123`; รหัสตัวเลขที่ Excel ทำศูนย์นำหน้าหายเติมให้ครบ 5 หลัก
- CID ในไฟล์ตัวอย่างทั้ง 4 ชุดถูกปิดบังด้วย `*` และมีค่าซ้ำ ห้ามใช้ CID ที่ปิดบังจับคู่บุคคล
- Upsert ใช้ `(fiscal_year, hoscode, pid, sex, birth, check_vhid)` ต้องตรงกันครบทุกส่วน ถ้าไม่มี PID ใช้ CID ตัวเลขครบ 13 หลักเป็นตัวระบุแทนโดยยังต้องตรง sex/birth/check_vhid และไม่จับคู่ข้ามไปยังแถวที่มี PID
- เมื่อ PID, sex, birth หรือ check_vhid ต่างกัน จะเป็นคนละคีย์ ไม่ใช้ CID สำรองมาเขียนทับข้ามคีย์ แม้ CID จะเหมือนกัน หากชีตเดิมมีคีย์เต็มซ้ำ ระบบหยุดให้ตรวจข้อมูลก่อน
- ตัวตรวจซ้ำก่อน upload ใช้ส่วนประกอบเดียวกับ backend (ปีและตารางถูกกำหนดสำหรับไฟล์นั้นแล้ว) ค่า sex ตัวเลข/ข้อความเทียบผ่านข้อความ; ค่าว่าง/null เป็นส่วนคีย์ว่าง ไม่ใช่ wildcard วันเกิดแบบ Date จากชีตแปลงเป็นวันตาม timezone ของชีตก่อนเทียบ YYYY-MM-DD
- แถวเก่าไม่มีปีงบประมาณไม่ถูกนำไปแสดงปนกับปีที่เลือกหรือ deactivate; ต้องระบุปีจริงหลังตรวจสอบต้นทาง

`source_columns` เป็น JSON array รายแถวของคอลัมน์ที่มีหลักฐานว่าเคยนำเข้ามา รักษาประวัติรายการคอลัมน์เมื่อไฟล์เก่าขาดฟิลด์ใหม่ และเพิ่มชื่อคอลัมน์จากค่าที่ไม่ว่างของข้อมูลเก่า ค่าว่างในชีตเก่าที่ไม่มี manifest ยังยืนยันไม่ได้ว่าไฟล์มีคอลัมน์นั้นจริง

## Upload / Update

อ่าน Excel (`xlsx`, `xls`) และ JSON array ใช้ parser เดียวกันใน preview และก่อนบันทึก ตรวจทุกแถวก่อนเริ่มส่ง รวมวันที่จริง คอลัมน์ที่ไม่รองรับ หัวซ้ำ รหัสบุคคลซ้ำ และชื่อไฟล์ EPI ที่ไม่ตรงกลุ่มอายุ หากพบฟิลด์ใหม่ที่ยังไม่รองรับจะหยุดพร้อมรายชื่อฟิลด์ ไม่ทิ้งเงียบ

- **เติม / อัปเดต (ค่าเริ่มต้น):** คอลัมน์ไม่ได้ส่งมาคงค่าเดิม เซลล์ว่าง/null ที่ส่งมาล้างค่านั้น ไม่ deactivate บุคคลที่หายจากไฟล์
- **ซิงค์ไฟล์เต็ม:** ใช้ไฟล์ครบทุกคนของหน่วยบริการที่มีอยู่ในไฟล์ หลังได้รับครบทุก chunk จึง deactivate รายชื่อที่ไม่อยู่ใน batch เฉพาะปีและหน่วยบริการที่ server ตรวจพบเอง หน่วยบริการที่ไม่มีสักแถวในไฟล์จะไม่ถูกล้าง
- เก็บ receipt ใน `epi_import_batches`: `batch_id`, `target_table`, `fiscal_year`, `mode`, `total_chunks`, `completed_chunks`, `hoscodes`, `status`, `updated_at`, `preflight` (ชีตเดิมได้คอลัมน์ `preflight` เพิ่มท้ายอัตโนมัติ)
- **Preflight (Issue #111, [ADR-0007](adr/0007-mandatory-import-preflight.md)):** `preflightEpiImport` (admin) รับเฉพาะฟิลด์ Record Identity (`hoscode`, `pid`, `cid`, `sex`, `birth`, `check_vhid`) แบ่งตาม chunk เดียวกับที่จะอัปโหลด พร้อม `batchId` ที่ client สร้าง (ซ้ำกับที่มีอยู่ถูกปฏิเสธ) จำนวน chunk ของ batch คือจำนวนกลุ่มที่ส่งมา ตรวจรูปแบบ identity ด้วย validator เดียวกับการนำเข้า แล้วสร้าง receipt สถานะ `preflight` โดยไม่สร้างหรือเขียนชีต EPI คอลัมน์ `preflight` เก็บ JSON ที่มีจำนวน (`matched`, `newRows`, `wouldDeactivate`, `activeBefore`, `outsideCohort`, `byHoscode` ซึ่งมี `outsideCohort` รายหน่วยบริการ), `risk` (`zeroMatchHoscodes`, `shrinkOverThreshold`, `outsideCohortBirthRange`), `cohortBirthRange` (`start`/`end` เป็นวันที่ ค.ศ. `yyyy-MM-dd` รวมทั้งสองปลาย, Issue #136), `outsideCohortFiscalYear` (ปีงบประมาณเดียวที่วันเกิดนอกช่วงทั้งหมดตรงกัน หรือ `null`), `requiredConfirmations` (`null` เมื่อปลอดภัย หรือ object ตัวเลขหนึ่งตัวต่อเงื่อนไขที่เข้า: `existingChildren` สำหรับเงื่อนไขเด็กเดิม และ `outsideCohort` สำหรับเงื่อนไข Cohort Birth Range), `shrinkThreshold`, ผู้ทำ preflight, SHA-256 ของคีย์รายชุดข้อมูล และ snapshot ของ receipt อื่นที่ทับหน่วยบริการเดียวกัน ส่วน `hoscodes` คงเป็น `[]` จนกว่าจะเขียนชุดข้อมูลแรก จึงไม่นับเป็นการนำเข้าที่ทับซ้อน การจับคู่กับแถวที่ปิดสถานะแล้วไม่นับเป็น "จับคู่กับเด็กปัจจุบัน" ในเงื่อนไขเสี่ยง เงื่อนไขและเกณฑ์ดู [features.md](features.md)
- `confirmEpiImport` (admin) รับ `typedNumbers` เป็น object ที่มี key เดียวกับ `requiredConfirmations` (Issue #136) ต้องเป็นผู้ที่ทำ preflight และตัวเลขทุกตัวที่ต้องพิมพ์ต้องตรงกัน จึงบันทึก `confirmedAt` และเขียน audit `confirm_epi_import` ตัวเลขตัวเดียวแบบก่อน #136 ไม่นับเป็นการยืนยัน และ receipt ที่ไม่มีผลตรวจ Cohort Birth Range (สร้างก่อน #136) ยืนยันไม่ได้ ให้เริ่มนำเข้าใหม่
- `upsertEpiData` ปฏิเสธ (fail closed) เมื่อไม่มี receipt จาก preflight, เมื่อเข้าเงื่อนไขเสี่ยงแต่ยังไม่ยืนยัน, (ก่อนเขียนชุดข้อมูลแรกเท่านั้น) เมื่อ receipt สถานะ `preflight` ไม่มีผลตรวจ Cohort Birth Range เพราะสร้างก่อน #136 (ให้เริ่มนำเข้าใหม่; batch ที่เริ่มเขียนแล้วเขียนต่อจนจบได้), เมื่อคีย์ของชุดข้อมูลไม่ตรงกับตอน preflight (สลับไฟล์), หรือ (ก่อนเขียนชุดข้อมูลแรกเท่านั้น) เมื่อ receipt อื่นที่ทับหน่วยบริการเดียวกันมีความคืบหน้าหลัง preflight (จำนวนล้าสมัย ให้เริ่มนำเข้าใหม่) เมื่อเริ่มเขียนแล้ว การเปลี่ยนแปลงของ batch อื่นไม่ทำให้ batch นี้ค้างครึ่งทาง ชุดข้อมูลแรกที่เขียนบันทึกจำนวนจาก preflight ต่อท้าย audit `upload_excel` ทุกการนำเข้า (เฉพาะจำนวน เงื่อนไข และการยืนยัน ไม่มีข้อมูลรายบุคคล)
- `cleanupEpiData` ปฏิเสธ receipt ที่ไม่มี preflight (receipt ก่อน Issue #111 ที่ค้างสถานะ `uploading` จึง finalize/deactivate ไม่ได้ ให้นำเข้าใหม่)
- `completed_chunks` เก็บ index และ SHA-256 fingerprint ของ payload; chunk ซ้ำเดิมไม่เขียนซ้ำ แต่ payload ต่างกันใน index เดิมถูกปฏิเสธ
- chunk ที่รับเข้าใหม่เก็บ metadata ซ่อมบันทึกตรวจสอบแบบ additive ใน entry เดิม (`audit`: actor จาก session ที่ยืนยันแล้ว userId/email จำนวน inserted/updated และขอบเขตการนำเข้า ตาราง/ปี/โหมด/ลำดับ chunk) เพื่อซ่อมสร้างเหตุการณ์ `upload_excel` ใน `audit_logs` จากข้อมูลต้นฉบับเมื่อการเขียน audit ล้มเหลวหลัง receipt ถาวรแล้ว และไม่เขียนซ้ำเมื่อเหตุการณ์นั้นมีอยู่แล้ว; receipt แบบเดิมที่มีเพียง index+fingerprint ยังอ่านและ replay ได้ตามปกติ โดยไม่สมมติ actor หรือจำนวนย้อนหลัง
- ใช้ ScriptLock ครอบการเขียน ป้องกัน batch เก่าที่ขอบเขตทับ batch ใหม่กลับมาเขียนหรือ cleanup
- การนำเข้าเป็นการเขียนทีละ chunk ไม่ใช่ transaction ทั้งไฟล์: ถ้าล้มเหลว แถวจาก chunk ที่สำเร็จอาจแสดงแล้ว แต่ batch ที่ไม่ครบ cleanup ไม่ได้ ให้นำเข้าไฟล์ครบใหม่ แล้วประมวลผล summary อีกครั้ง
- Metadata ระบบและ AI ไม่รับจากไฟล์นำเข้า; ค่า AI เดิมรักษาไว้ ไม่ถือว่าเป็นผลวิเคราะห์ใหม่หลังข้อมูลเปลี่ยน

## มุมมองที่ 1

รายการวัคซีนทั้งหมด (หน้ารายบุคคล หัวข้อ "รายการและขอบเขตการประเมิน" ประวัติ และ Excel พร้อมวัคซีนตามอายุ) ดึงจากชีต `vaccine_rules` โดยกรอง `fiscal_year`, `age_group`, `view_type = 1`, `is_active` — ไม่มีรายการ hardcode ฝั่ง frontend อีกต่อไป การเรียงลำดับใช้ `sortRulesForDisplay` (อายุเป้าหมายน้อย→มาก ที่ไม่ระบุไว้ล่างสุด แล้วเรียงตามกลุ่มวัคซีนและชื่อแสดงผล) การประเมินรายบุคคลและการคำนวณ summary ใช้ `evaluateDynamicV1()` กับ rules ชุดเดียวกันผ่าน `markSourceAware()`

- กฎ View 1 ที่ตั้ง `is_required_for_v2 = false` ถือเป็น **นอกแผน**: แสดงในรายการประกอบ แต่ไม่นับในความครบถ้วน (เช่น PCV 1–3 ของ 1 ปี)
- คอลัมน์ผลในหน้ารายบุคคลแสดง badge **ครบ / ตรวจสอบประวัติ / ไม่ครบ** พร้อม tooltip บอกเหตุผล (ขาดเข็ม, ยังไม่ถึงเกณฑ์, ข้อมูลไม่พอประเมิน, คำเตือนวันที่) และกรองได้ตามสถานะเต็ม 5 ค่า — คำเตือนวันที่เป็น "ตรวจสอบประวัติ" ไม่ใช่ไม่ครบ (Issue #102, [features §3.6](features.md)) รายละเอียดผลใน Excel/PDF มีข้อสังเกตวันที่ด้วย
- ค่าเริ่มต้นของแต่ละปีมาจาก `seedVaccineRules` (กฎ default) และ admin ปรับแก้/clone ต่อปีได้ในหน้า Rules Engine

รายการที่ไม่มีกฎ active ตรงกับฟิลด์ต้นทาง ไม่ยืนยัน mapping หรือไม่มีข้อมูลคอลัมน์เพียงพอ แสดง **ข้อมูลไม่พอประเมิน** แยกจากยังไม่ถึงอายุและไม่พบวันที่ ไม่คิดเป็นขาดวัคซีนและไม่นับในตัวหาร summary จำนวนรายการที่ไม่พอประเมินแสดงแยกใน Dashboard

รายการมีทางเลือก (BRANCH): ตัดสินได้ต่อเมื่อไฟล์/`source_columns` ยืนยันคอลัมน์ครบ **ทั้งสองทางเลือก** หากยืนยันคอลัมน์ทางใดทางหนึ่งไม่ได้ รายการนั้นเป็น "ข้อมูลไม่พอประเมิน" ทั้งรายการ รวมเด็กที่ครบชุดทางที่มองเห็นแล้ว (Issue #78) เพราะการประเมินเฉพาะคนที่ผ่านทางที่เห็นทำให้ตัวหาร summary เหลือแต่คนผ่าน แล้วแสดง coverage เทียม เช่นไฟล์มี `rv21/rv22` (หรือ `j11/j12`) แต่ไม่มีคอลัมน์อีกชุด รายการนั้นต้องแสดง "ยังประเมินไม่ได้" (ตัวหาร 0) ไม่ใช่ 100% แถวเก่าที่ไม่มี manifest ถือค่าที่ไม่ว่างเป็นหลักฐานคอลัมน์: ทางเลือกใดไม่มีค่าเลยยืนยันไม่ได้และอยู่ในสถานะเดียวกัน จึงเหลือเฉพาะแถวที่มีค่าครบทั้งสองทาง (ซึ่งผ่านเกณฑ์อยู่แล้ว) ที่ยังประเมินได้ — ต้องนำเข้าไฟล์ที่มีคอลัมน์ครบอีกครั้งจึงจะประเมินทั้งกลุ่มได้

### Mapping ที่ยังต้องยืนยันจากเจ้าของข้อมูล

- OPV 6 เดือน: ยืนยันแล้ว (Issue #109) — รหัส HDC 083 = `opv3_date`
- `opv1_date`/`opv2_date`: ยืนยันแล้ว (Issue #121) — เป็นวัคซีนที่มีส่วนประกอบโปลิโอเข็มที่ 1/2 **ชนิดใดก็ได้** (OPV หรือ IPV) ตามลำดับที่ HDC เรียง ไม่ใช่เฉพาะรหัส OPV 081/082 จึงใช้เป็นหลักฐาน "ได้ OPV แทน IPV" ไม่ได้ ใช้ได้กับกฎสูตรโปลิโอเดิมของเด็กเกิดก่อน 1 พ.ค. 2566 ดู [research §3.1, §3.3](research/hdc-je-indicators-and-epi-schedule-2569.md)
- HBV 4/6 เดือน: ยืนยันแล้ว (10 ก.ย. 2569) โครงสร้าง HOSxP สลับคอลัมน์ — `hbv4_date` เก็บเข็ม 4 เดือน (โดส 3), `hbv3_date` เก็บเข็ม 6 เดือน (โดส 4) สอดคล้องกับ `TARGET_AGE_MONTHS_BY_FIELD` และคู่เข็มใน date_checks ที่ generate ตอน seed
- PCV 1 ปี: ไฟล์ 2 ปีไม่มี `pcv4_date`; ไม่เดาว่า `pcv1`–`pcv3` เป็นเข็ม 1 ปี
- JE3: ปิดแล้ว (Issue #127) — ไฟล์ HDC ไม่ export `je3_date` ทุกกลุ่มอายุ กฎ JE ของ 3/5 ปีจึงเป็น LAJE อย่างเดียว ไม่อ้าง `je3_date` อีก (ดู `docs/features.md` มุมมองที่ 2 อายุ 3 ปี); schema ยังรับ `je3_date` ไว้สำหรับไฟล์ที่ export ในอนาคต

การยืนยันครั้งต่อไปให้แก้กฎในชีต `vaccine_rules` (หรือ seed default พร้อม contract tests) — ไม่ใช้ `seedVaccineRules(..., true)` กับปีที่มีกฎแก้ไขแล้ว เพราะจะ reset กฎทั้งปี

## มุมมองที่ 2 และ export

ผลรายบุคคลตัดสินด้วยกฎ View 2 โดยแสดง `result` จาก HDC ประกอบพร้อมป้ายผลไม่ตรงกัน (Issue #101 — ดู [การแสดงข้อมูลรายบุคคลจาก HDC](hdc-record-display.md)) ประวัติแสดงทุกเข็มที่โหลดมา รวมหน่วยฉีด/หน่วยบันทึก เพิ่มที่อยู่ ประเภทพื้นที่และรหัสหมู่บ้าน Excel เก็บคอลัมน์วัคซีนและกลุ่ม HDC ครบ ส่วน PDF เป็นรายชื่อพร้อมที่อยู่/ประเภทพื้นที่ ผลตามกฎและผลจาก HDC ไม่ใช่ประวัติครบทุกเข็ม

วันที่ในหน้าประวัติทั้งสองมุมมองแสดง `DD-MM-YYYY` โดยยึดส่วนวันที่ของข้อความต้นทาง เช่น `2023-10-03T17:00:00.000Z` → `03-10-2023` ไม่เลื่อนตาม timezone เบราว์เซอร์ ไม่แก้ค่าที่จัดเก็บหรือคอลัมน์วันที่ต้นทางใน export

มุมมองที่ 1 export เฉพาะวัคซีนในกลุ่มอายุ; มุมมองที่ 2 export ทุกคอลัมน์วัคซีนที่โหลดมา การกรองประเภทพื้นที่ไม่ได้เปลี่ยนประชากรเป้าหมายโดยอัตโนมัติ

Summary View 2 และผลรายคนคำนวณด้วยกฎภายในชุดเดียวกัน (Issue #101) ตั้งแต่ Issue #89 กฎ V2 แต่ละข้อผ่านประตูตรวจคอลัมน์ต้นทางรายกฎเดียวกับ View 1 (`ruleSourceDecidable`; BRANCH ต้องครบทั้งสองทางตาม Issue #78) — กฎที่ไฟล์/`source_columns` ยืนยันคอลัมน์ไม่ได้ไม่ถูกนับเป็นขาด เด็กที่มีกฎเช่นนั้นแม้ข้อเดียวและไม่มีเข็มที่ขาดจริงเป็น "ประเมินไม่ได้" (เด็กที่ขาดเข็มจริงยังเป็นไม่ผ่านและอยู่ในรายชื่อตามฉีด — Issue #103) ออกจากตัวหารความครบคลุมและถูกนับแยกใน `view2NotEvaluableCount` (สัญญาแบ่งกลุ่มดู [`schema.md`](schema.md) `Dashboard_Summaries` — เด็กที่มีแต่คำเตือนวันที่นับแยกใน `view2ReviewCount`, Issue #102) `result` ของ HDC ไม่เปลี่ยนการจัดกลุ่ม (ลำดับความสำคัญดู [features §3.1](features.md)) และรายชื่อกลุ่มประเมินไม่ได้เป็นงานคุณภาพข้อมูล (ขอไฟล์ใหม่) ไม่ใช่รายชื่อตามฉีดวัคซีน

## การย้ายขึ้นระบบจริง

1. สำรองชีต EPI, vaccine_rules, Dashboard_Summaries และตรวจปี/identity ซ้ำก่อนย้าย schema
2. Deploy backend ที่ deployment เดิมให้คง `/exec` URL แล้ว deploy frontend รุ่นนี้คู่กัน ไม่ใช้ client เก่าอัปโหลดหลาย chunk กับ receipt รุ่นใหม่
3. ใช้ `setupDatabase()` จาก Apps Script owner หรือ endpoint `setup` ที่ตรวจสิทธิ์ admin/superadmin แล้ว ระบบเพิ่มคอลัมน์ท้ายชีต ไม่เลื่อนข้อมูลเดิม; upsert ก็เพิ่มคอลัมน์ที่ขาดให้ก่อนเขียนได้
4. นำเข้าไฟล์ HDC เดิมใหม่ในโหมดเติมข้อมูลเพื่อเติมคอลัมน์ที่เคยถูกทิ้ง ตรวจจำนวนคนและรหัสศูนย์นำหน้าในทุกอายุ
5. ประมวลผล Dashboard ใหม่ทุกปีที่ใช้งาน (ทั้งปีและไตรมาส); ค่า cache เดิมยังไม่สะท้อนรายการอายุจนกว่าจะประมวลผลใหม่
6. ตรวจเบราว์เซอร์จริงทั้ง desktop/mobile, ทั้งสองมุมมองและไฟล์ export รวม login ของ admin/superadmin/user ต่างหน่วยบริการ

`getEpiData` ต้องมี session; ขอบเขต user อ้างอิงหน่วยบริการจากบัญชี ไม่เชื่อค่าที่ client ขอ `debugBounds`/`debugGetEpiData` ถูกนำออกจาก route ข้อมูลรายบุคคล ไฟล์ HDC ตัวอย่างไม่ได้ commit เข้า Git
